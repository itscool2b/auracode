# Desktop customization

Customize is available below Search and New chat. It is a shortcut into Settings, which holds Plugins & MCP, Instructions and Project memory beside Agents and the app's own pages (owner's plan, 4 November 2026: one screen with search). Opening Settings keeps the current chat and its draft mounted. A page keeps its unsaved editors while other pages are visited, until Settings closes. Chat-specific Instructions opens on that chat's own folder or worktree.

The project header's plus opens the existing new-chat flow with that project selected. A sole usable folder is preselected; otherwise Aura uses the most recently used valid folder within that project. A retained managed worktree resolves to its source folder within the same project. Missing mappings remain unresolved. Delayed discovery never replaces a deliberate folder choice, and canceling the folder picker retains the prefill. The project agent preference takes priority over the profile preference, and detection never replaces a deliberate agent selection. Folder and worktree review, setup commands, busy-folder warnings and creation safeguards still apply.

## Session controls

The composer separates access and workflow controls from the agent, model and effort picker. Model and effort choices come from the live connection. Switching agents uses the existing reviewed continuation flow. A native control's requested, effective and pending values are distinct; a saved option that disappears does not silently grant broader access.

Native Plan is separate from rendered plan progress. Codex uses its advertised collaboration mode, Claude uses native permission mode while remembering execution access, and ACP uses advertised native mode options. Connections without an advertised planning workflow explain that limitation. Leaving Plan through Aura requires explicit implementation approval. Changes to live native access or workflow require an idle session without queued messages or pending requests.

Access does not wait for the agent to run. Each connection's catalog keeps the native access and workflow controls and the access levels it last reported, so a chat whose agent is not running (one opened after a restart, a new chat whose agent is still starting) names the access its next start asks for instead of "Access unavailable". A stopped chat takes an access change for that start, native or level, and the start's setup asks for it. Once a starting agent's process has its setup, a change waits until the agent is ready: the picker shows the choices disabled until then, and the session refuses one rather than keep it, so a message sent meanwhile never runs on access the person had just left. "Access unavailable" means only that a running agent offers no access control. A mode change always waits for a running, idle agent.

A new chat starts its agent as it is made, before its first message. Claude Code writes a session's file only with that message, so a saved Claude session that ran no turn and has no file starts again under its own ID rather than being resumed (which Claude refuses). A session that ran turns always resumes, so a missing file is reported, never quietly replaced.

These preferences live in additive versioned `controls_json` state per agent session. They do not overload legacy `Autonomy` or replace `config_json`. Unsupported saved preferences block dispatch until an offered value is chosen. Acknowledgements belong to the current generation; stale replies cannot overwrite a newly attached session.

## Plugins and shared MCP

[Plugins & MCP](plugin-library.md) lists each agent's native inventory and reviewed management capabilities. It uses structured native commands where available and a reviewed terminal route for operations that have no structured interface. The renderer consumes backend capability descriptions rather than maintaining provider-specific command tables.

Shared MCP definitions default to the selected project and can also apply across the profile. A project override replaces an all-projects definition with the same Aura ID. Definitions and conflict history use the profile writer; account profiles encrypt and sync portable revisions. Local environment and header credentials are stored separately and never included in a portable export or sync envelope. OAuth sessions remain with the native agent. Importing a native definition is explicit and leaves the original file intact.

Importing a Local project into an account carries its memory, memory proposals and admitted prompt snapshots, plus project MCP definitions and revision history. It does not copy profile-wide MCP definitions or local credentials. Required credentials must be configured separately in the destination profile.

Each new or resumed native generation receives a resolved snapshot. Codex receives thread configuration, Claude receives an additive session descriptor, qualified Pi receives a temporary extension, and ACP receives advertised MCP transports. Native names are checked for conflicts. Unsupported connections or transports report their limits. Restarting an idle session applies changed definitions without replacing native configuration. A direct connection test only verifies MCP initialization; it does not claim an agent session has connected.

## Project memory

Each project has one Markdown document shared across its folders and worktrees. Aura stores its revisions, reasons and proposal history in the profile database. Account profiles use the existing encrypted storage and encrypted sync path. This is an Aura document, independent of `AGENTS.md`, `CLAUDE.md`, and harness-native memory. The editor explains that distinction.

On 1 November 2026 the owner reversed the earlier review-only decision: agents now edit project memory directly by default. The profile preference `agent_memory_writes`, the "Let agents edit memory directly" switch in Settings > Project memory, turns this off and returns agents to propose-and-review. The switch reaches running chats at once, because every memory grant reads it on each request. Existing profiles take the new default.

An agent's direct edit is a normal revision whose source names its chat (`agent:<chat id>`), saved against the base revision the agent read. A different edit from a stale base fails and tells the agent to read again; retrying an identical write answers the current revision without adding one. The 16 KiB and reason limits are the editor's. History names the chat (its title when known, otherwise "An agent"), shows each revision's changes against its parent, and offers one-click Restore, which saves that text as a new revision of the user's against the current revision. Users save against an expected revision too. An open editor reads memory again after every change and on window focus, but never replaces a draft: it says a newer version exists and offers a comparison.

Every agent edit is visible, which is how Aura mitigates a prompt-injected agent persisting instructions into memory without blocking legitimate edits. The chat pane shows a calm banner naming the chat, with Review, which opens Settings > Project memory on the edit's changes, and Undo, which restores the revision before the agent's consecutive edits as a new user revision, and only while memory is still at their result. When the current revision came from an agent, the attached reference text says so on the line after its header, so later agents weigh it as reference rather than the user's instructions.

While direct edits are off, agents propose a complete replacement with its base revision, reason and idempotency key, and only user-facing acceptance creates the revision. A stale proposal cannot overwrite newer memory; it must be reconciled in the editor. Agents may also propose while direct edits are on, when they want the user's review first. Importing Markdown or a memory export creates a new reviewed revision. Exported history and proposals remain reference data rather than imported approval state.

Memory is attached visibly as reference text to a real user message on the first native-generation turn and whenever the accepted revision changes. Current user requests and instruction files take precedence. Aura persists the exact admitted revision with the turn before sending it. Retry and edited continuation retain their original admitted memory bytes; a later edit does not silently rewrite historical context. No memory-only model turn or hidden system prompt is generated.

The app-owned service exposes read, write and propose operations; write answers only while the switch is on, and otherwise tells the agent to propose. A loopback listener and random token bind access to the owning chat, project, profile and native generation. Stopping, failing or retiring the session revokes that grant. The bundled `aura-project-memory` skill describes the tools (`aura_memory_read`, `aura_memory_write` and `aura_memory_propose`), and the app's `--aura-memory-helper` mode provides a stdio bridge without exposing database paths or account keys. The optional MCP helper is used only on compatible native connections. Remote or unsupported connections retain visible reference context and explain why edits cannot be delivered. Every committed change sends the window `auracode-project-memory-changed`, naming an agent's direct edit; revisions that arrive by account sync are read again after the exchange.

## Verification boundary

Browser previews use synthetic data and production components. They verify layout, navigation, keyboard behavior and accessibility, not native CLI or authentication behavior. Native protocol probes use isolated temporary homes and local synthetic MCP servers without model prompts. Embedded Windows smoke tests exercise the actual Tauri command and storage path. These are distinct forms of evidence; neither establishes macOS release acceptance or a golden visual baseline.
