# Browser: a real browser beside the chat, for you and your agents

Owner, 9 November 2026 (drawn on the canvas): the header's opener "opens up your browser" beside the
chat, "a nice browser" with "password", "search history, pretty much everything that Codex browser
has"; it is "some sort of plugin or skill" that teaches agents browser use, listed in Customize as a
"universal plugin" that cannot be added or removed, only turned off, "on by default", and turning it
off "disables the browser on the UI"; Chat only, not Terminal; and an annotation mode: "click
annotate ... highlight a certain area ... it spawns like a little tiny chat with a model picker ...
copying cursor in terms of like their annotate mode", or "add it to like this general chat".
"Handle all edge cases", "test the fuck out of the functionality", "ship the whole thing".

## What the references do

- **Codex** (OpenAI, April 2026; learn.chatgpt.com/docs/browser): an in-app browser beside the
  chat (split view) or full view, Ctrl+Shift+B to show it, Ctrl+T for a tab. It keeps its own
  profile and history, separate from the person's browser; sign-ins persist. The address bar
  searches history and sends anything else to a search engine. Settings > Browser holds history
  (search, reopen, remove) and Clear browsing data, and downloads. Annotate: click an element or
  drag an area, write a comment, then send a message asking the agent to address it. The agent
  opens pages, clicks, types, inspects state and takes screenshots; page content is untrusted.
- **Cursor** (Design Mode, Annotate; cursor.com/docs/agent/design-mode and /browser): the browser
  is a pane in the agent layout. Annotate in its toolbar (Cmd+Shift+D): click an element to open
  a note, Arrow Up and Down move the highlight to the parent or child before clicking, Shift-click
  adds elements to the same note, drag boxes an area, Esc backs out one step at a time. A note
  sends at once, or collects as numbered pins (Batch edits) behind one Send; a shortcut puts it in
  the chat input instead. Each element carries its tag, id, classes, attributes, a selector path,
  the first 200 characters of text, size and position, six computed styles, the React, Vue or
  Svelte component and its stack, and a screenshot cropped to it. Agent tools: navigate, click
  (double, right, hover), type, scroll, screenshot, console and network; an MCP server with a
  per-session token and a random id per tab.
- **Aside** (aside.com): a Chromium browser whose agent works in the sites you are signed in to,
  with a password manager that keeps credentials from the AI.

## Decisions

1. **A real engine, not an iframe.** Most sites refuse to be framed, and a frame shares the app's
   origin rules. Each tab is a native webview (wry 0.57.1, the version Tauri already runs: WebView2
   on Windows, WKWebView on macOS, WebKitGTK on Linux) placed over the panel's page area.
2. **No auracode IPC in a guest page.** Tauri's own child webviews carry its IPC script, invoke
   key and app protocols, and take the IPC origin from the request's `Origin` header, so a page
   that framed `http://tauri.localhost` would run app commands as local. Guest tabs are raw wry
   webviews with no Tauri protocol or command. Their only channel is wry's message handler, which
   accepts a few typed messages (a pick, a shortcut, a location change), each checked against the
   page the engine says sent it.
3. **Its own profile.** Cookies, storage and saved passwords live in `<profile>/browser`, apart
   from the person's browser and from the app's webview, and sign-ins persist. An encrypted
   account profile keeps no browser data on disk: its tabs browse privately and its history stays
   in memory.
4. **Beside the chat, where Changes was.** The header's panel button (the "opener") opens the
   browser as a split beside the conversation, with a divider that drags; Full view takes the
   whole pane. Changes moves to its own header button (a diff icon), keeps Ctrl+J and Review, and
   shares the side with the browser and the task panel: opening one replaces the other.
5. **One browser per chat.** Each chat has its own tabs, restored after a restart; the profile's
   cookies are shared, so a sign-in works in every chat. A new tab is auracode's start page (the
   chat's Run address, recent and frequent pages), not a web page.
6. **The plugin is universal.** Settings > Plugins & MCP starts with Universal plugins: Browser,
   built in for every agent, on by default, with a switch and no Add or Remove. Off closes every
   tab, hides the opener and Annotate, and gives agents no browser tools (a running session's
   tools answer that it is off).
7. **Agents use it through MCP.** Like the project-memory helper, the app's own executable runs
   as a stdio MCP server (`--aura-browser-helper --mcp`) that a native Chat session's agent starts,
   reaching the app over a loopback listener with a per-session token; the session's end revokes
   it. The server's instructions teach browser use (the skill): open, read the page as an outline
   with refs, act on refs, screenshot, console and network, evaluate. Terminal chats, remote hosts
   and agents without MCP get no browser tools; the panel still works for the person.
8. **Passwords stay out of the agent's reach.** On Windows, WebView2's own password manager
   offers to save a sign-in and fills it from its suggestions, encrypted by Windows; the page
   outline never shows a password field's value. Clear browsing data removes saved passwords.
9. **Annotate freezes the page while you write.** Picking runs in the page (a highlight, a label,
   Arrow Up/Down, Shift for more, drag for an area). Once picked, the panel swaps the live page
   for its screenshot with the selection drawn on it and opens a small composer beside it: the
   chat's own model and thinking picker, Send, and Add to chat. Send posts the note, the element
   context and the cropped screenshot to this chat (queued if a turn runs); Add to chat puts them
   in the message box instead, for one message about several annotations. Choosing another agent
   in its picker is the composer's usual move to that agent, and the note waits for it.
10. **Native views sit above HTML.** Anything that opens over the page area (a menu, a dialog, the
   palette, a toast, the address bar's suggestions) swaps the live page for its screenshot until
   it closes, so it reads on top.

## Edge cases

Window minimized, restored or moved to another display; panel resized, sidebar collapsed, Full
view, a narrow window; chat switched, Settings or the Dashboard opened over the chat; appearance
and theme changes; a page that never loads, a crashed page, a hung script, a page with an open
`alert`; `window.open` popups that sign in and close themselves; downloads; links to other
programs (`mailto:`, `vscode:`); `file:` pages and localhost dev servers on any port; many tabs
(at most ten live pages, the rest asleep until shown); an agent browsing a chat that is not on
screen; two agents in two chats at once; a stale ref; a plugin turned off mid-turn; a profile
switch; quitting with pages open; Terminal mode; keyboard use throughout; reduced motion.

## Order of work

1. The native host: tabs as child webviews, placement, navigation, titles, history, downloads,
   new windows, shortcuts, persistence, the page script (outline, actions, console, network,
   annotate), Windows extras (DevTools protocol input and screenshots, back and forward state,
   crashes, closing popups, saved passwords).
2. The panel: header, tab strip, toolbar, address bar with suggestions, start page, history,
   occlusion, Full view, the divider; Changes moved.
3. Agent tools: the grant, the helper, session wiring, reserved names, the switch.
4. Annotate: the picker, the frozen page, the small composer, Send and Add to chat.
5. Settings: Universal plugins, Settings > Browser (history, data, passwords).
6. The fixture (`?preview=browser`) and its check, unit tests, a native end-to-end run against a
   real page with a real agent, the visual language.
